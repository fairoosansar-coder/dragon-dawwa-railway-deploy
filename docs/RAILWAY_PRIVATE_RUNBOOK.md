## Architecture to prove, not a verified live service

One *future* Singapore Railway app service would use [`deploy/railway/Dockerfile`](../deploy/railway/Dockerfile), a separately pinned Tailscale image and the existing Node server. Its entrypoint [`start-private.sh`](../deploy/railway/start-private.sh) rejects a wrong project/environment, non-loopback application bind, non-`*.ts.net` HTTPS origin, missing persisted Tailscale volume, direct public DB URL, root app DB credential and absent secret. It runs `tailscaled` in userspace, checks its exact DNS name, resets the dedicated node's prior Serve configuration, enables **Serve only** to `http://127.0.0.1:3000`, refuses detected Funnel and stops the app when either process exits. The Tailscale node state must persist in a **dedicated app-service volume mounted at `/var/lib/tailscale`**; the Railway-provided `RAILWAY_VOLUME_MOUNT_PATH` is required to match. A Tailscale auth key is needed for the first login and later reauthentication if the persisted node state expires. The key is never built into the image.

A separate *future* Railway MySQL 8 service would stay **private, no TCP proxy**, in the **same project/environment and Singapore region**. Railway private DNS (`mysql.railway.internal` or its actual service name) crosses encrypted WireGuard. The narrowly scoped `REVIEW_DB_TRANSPORT=railway-internal-wireguard` exception in `server/db.mjs` requires this exact project/environment, `AUTH_PROVIDER=tailscale-serve`, loopback bind, internal `.railway.internal` hostname, no URL options, no VM socket and **either** `REVIEW_DB_ROLE=app` with `dd_app` **or** `REVIEW_DB_ROLE=migrator` with `dd_migrator`. The web startup requires the app role. `mysql2` connects IPv6-only through a socket factory. Managed external MySQL keeps verified TLS; the separate VM mode keeps its guarded Unix socket. This is not proof that the uncreated Railway MySQL service has connected successfully.

**The app must never use the template's default root `MYSQL_URL`.** At first provisioning, the operator must create a *fresh* schema exactly `dragon_dawwa_private_railway` and distinct dedicated `dd_app` and `dd_migrator` users using a protected console inside that private DB service; grant `dd_app` only SELECT/INSERT/UPDATE/DELETE and `dd_migrator` only the required CREATE/ALTER/DROP/INDEX/REFERENCES plus DML. Store independent credentials through Railway's protected variable editor, not chat or source. **Before giving the migrator access**, a privileged operator must independently inventory **tables/views, routines, events and triggers** in this exact new schema and verify all are zero; MySQL can hide objects in `information_schema` from accounts without visibility privileges ([trigger metadata rule](https://dev.mysql.com/doc/refman/8.0/en/information-schema-triggers-table.html), [routine visibility rule](https://dev.mysql.com/doc/refman/8.4/en/stored-routines-privileges.html)). The operator-only [`bootstrap-railway-db.mjs`](../scripts/bootstrap-railway-db.mjs) requires `REVIEW_DB_ROLE=migrator`, an explicit confirmation flag, an independently specified exact expected schema, a private migrator URL and a database lock. It repeats a **migrator-visible** zero-object inventory across all four metadata classes as defense-in-depth, then applies seven migrations and verifies schema. **Never run it against the original Site, the current review DB, or a populated schema.** Normal Node startup performs read-only schema verification and must fail if bootstrap has not succeeded. Railway pre-deploy commands do not mount volumes, so the node's state and bootstrap cannot be treated as pre-deploy volume steps.

**Ingress must remain private.** No Railway generated domain, public TCP proxy, Funnel, DNS record, public signup or inbound `0.0.0.0:3000` listener. There is intentionally no app-port `EXPOSE` in the Railway-only image. The container-local Docker health check is not an authorization test; a Railway platform HTTP health check that requires a routable service IP may fail against a loopback-only app, so do not enable such a check blindly. Prove real Serve HTTPS, `Tailscale-User-Login` identity injection, no tagged-requester or Funnel fallback, grants limited to owner/tester, role revocation and node persistence **on the deployed platform** before sharing a URL. A source simulation cannot prove these facts.

3. **Only after approval:** provision resources in the *new* empty project, not the pre-existing Hobby projects. Verify actual Serve/no-domain/no-Funnel, and obtain the owner's **verified** tailnet login before granting the first role. Do not use a claimed email to bootstrap an owner.
4. **Disaster recovery:** acquire an independently controlled private S3 bucket and implement the Railway job, verify encrypted logical upload **and byte-identical download** plus a disposable **MySQL 8** restore, row/constraint/read-write checks, and daily alerting. Railway volume snapshots are supplemental and are lost with their project/volume failure. Approve retention and purge ownership before outside personal intake.
5. **Real acceptance:** one separate consenting person signs in with their own tailnet account on a physical iOS Safari or Android Chrome device. Check invitation, logout-all/revocation, EN/Tamil/Sinhala source and human review, Quran recitation, user-triggered WAV play/pause/seek/speed/replay/no autoplay and isolated personal data. Synthetic JWTs and touch-emulated Chromium are **not** second-user/physical-device evidence. Only after the owner accepts all private gates may the stable tailnet URL be handed to approved testers; public community launch remains separate.
