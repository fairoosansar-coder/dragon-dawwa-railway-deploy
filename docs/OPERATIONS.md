## Roles and real daily work

| Verified role | Permitted action | Explicit boundary |
| --- | --- | --- |
| Reader/member | Visitor content; own profile, saved items, Quran place, optional private study history/audio and export/delete | Cannot read others' learning or staff records; profile fields never grant a role. |
| Author | Own language-specific drafts at `/admin` | Cannot approve or publish. |
| Reviewer | Review submitted **exact revision and each language**; request changes or acknowledge approval; read event/correction queues | Approval is a workflow action, not a credential, hadith grading or scholarly endorsement. |
| Publisher | Publish/withdraw approved snapshots; manage genuine events; curate checked external links and reviewed correction overlays | Cannot access the owner-only private inbox, member contact or owner settings. |
| Owner | All above; exact-ID role grants/revocations, minimal member index, owner-only inbox, audit, model-usage/report triage and bounded safe settings | Cannot remove the last owner; no setting purchases a service, publishes a site, modifies DNS or purges data automatically. |

- Quran Foundation reader credentials were supplied through a protected runtime entry, not source or chat. The key is read from the protected server environment and never returned to browsers; durable host must provision it through protected secret entry. Four integrated **successful** private text generations (English twice, Tamil, Sinhala) consumed **2,368 reserved input characters** in the app's usage ledger; one integrated **591-character** explanation produced a 2,492,464-byte (~51.93-second) private WAV. Three additional short voice samples were generated directly for owner review and are **not** in that app usage ledger. No model token invoice, account tier or actual billed amount was available.
- Official [Google API pricing](https://ai.google.dev/gemini-api/docs/pricing) reviewed on 5 October lists paid-standard Flash-Lite text input/output rates and an approximate speech rate of **$0.0015 per 10 seconds**; at that published illustration the measured 51.93-second WAV is roughly **$0.00779 for speech output**, excluding input and any account-specific terms. This is **not an actual billed charge, budget guarantee or hard monetary cap**. Confirm the Google project's billing tier and [terms](https://ai.google.dev/gemini-api/terms) before expanding beyond the owner canary; free versus paid data-use terms differ. The application does not send an account ID to Quran.ai/Google, but it does send the opted-in question, fetched source excerpts and, for microphone transcription, audio. Never enter private or sensitive facts into study questions.
- Private generated audio is stored in the review MySQL `study_audio` table with an owner-bound response and idempotent content/language/model/voice key; the protected endpoint rechecks role/ownership and serves `no-store` WAV. It is not temporary container disk. This limited pilot design may require approved off-database private object storage before broad traffic. Quran recitation remains provider-original; Google never impersonates a reciter. Safari/Android and native pronunciation were **not** certified.

## Seven additive migrations, backup and failure recovery

1. The explicit operator-ledger order is `001_core`, `002_community`, `003_members`, `004_member_integrity`, `005_sessions`, `006_manage`, `007_study` — **30 tables** in the isolated review MySQL. Normal HTTP startup runs read-only schema/foreign-key verification and **never DDL**. Application writer roles should be least-privilege; production accounts/data must be separate.
2. Before any further DDL, pause writers, create an AES-256-GCM snapshot with `BACKUP_PASSPHRASE` supplied by a protected operator environment and `node scripts/review-backup.mjs backup /restricted/snapshot.enc`, verify with `node scripts/review-backup.mjs verify /restricted/snapshot.enc`, then use `node scripts/migrate-review.mjs /restricted/snapshot.enc`. The migration command checks a backup, orphan rows and advisory lock. **Do not run it on the original Site or production database.**
3. The encrypted full-schema snapshot was first restored into a **disposable MariaDB schema**, then independently into an extracted **MySQL 8.0.46** Unix-socket-only instance with TCP disabled: seven migrations, all **30 tables**, exact normalized rows, **18 foreign keys**, 30 primary keys, six unique constraints, and a rolled-back synthetic member/save read-write passed. Both disposable QA data and snapshot/passphrase were removed after testing; there is **no extant off-host backup or recoverable snapshot from this drill**. Neither rehearsal proves the proposed VM's exact MySQL installation or an already-running remote backup. Establish the separate key custodian, private bucket and live schedule before relying on any release.
4. Roll back code only after checking that the older code understands migration 007. Never blindly drop columns or restore an old snapshot over newer member actions. For data recovery: freeze writes, capture a fresh encrypted snapshot, rehearse the earlier encrypted snapshot in isolation, reconcile later writes/deletions, and request owner authorization for any live restore. No production D1 import, production delete or original-Site change occurred.
5. `/staff#settings` supports **count-only retention dry runs** and a provisional configurable period; automatic purge stays disabled until the owner approves a schedule and operator. The provisional 90-day active intake / 12-month tombstone / 30-day backup expiry from `docs/RETENTION.md` is **not active automation**. Session revocation rows expire logically; purge and off-host backup scheduling remain to be approved. There is no hosted job-alert channel for unattended failures yet.
